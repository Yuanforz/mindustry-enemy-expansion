# 指挥层：算法调查与设计（2026-10-21）

## 为什么要做

Operations 目前只有经济这一层是优化：给定目标（比如"1 座 stell 工厂满负荷"），求最短建造顺序和布局。它上面那一层——什么时候扩经济、造什么兵、什么时候设防、地图任务先做还是后做——是测试程序 `Match` 里写死的阶段表，输了就往上加规则，和 Brain 的路子一样。这一层要换成真正的优化：预测、模拟、比较、选择。

## 调查：已有的算法

| 方向 | 算法 | 要点 | 和我们的关系 |
|---|---|---|---|
| 建造顺序 | Churchill & Buro 的 BOSS（深度优先分支定界，[AIIDE 2011](https://ojs.aaai.org/index.php/AIIDE/article/view/12435)） | 把建造顺序当成"资源受限、可并行、最小化总工期"的调度问题；只管经济和生产，不管战斗 | 就是我们经济规划器做的事。我们的规划器已经覆盖，还额外处理布局 |
| 调度求解器 | OR-Tools CP-SAT（[调度文档](https://github.com/farao-community/or-tools/blob/stable/ortools/sat/doc/scheduling.md)） | 区间变量、累积约束、最小化工期，有 Java 接口 | 以后可用来精修建造顺序；要带本地库，模组打包麻烦，暂不引入 |
| 战斗估算 | Lanchester 平方律（[Stanescu 等 2015](https://ojs.aaai.org/index.php/AIIDE/article/view/12780)，[TS-Lanchester²](https://arxiv.org/pdf/1605.05305)） | 战力 ≈ 总伤害/秒 × 总血量；单位强度从实战记录拟合；用来决定进攻还是撤退，胜率高于直接模拟 | 控兵层已经在用。指挥层的力量预测也用它；炮塔用防御规划已有的实测容量表 |
| 宏观规划：脚本上的搜索 | Puppet Search（[Barriga 等，AIIDE 2015](https://ojs.aaai.org/index.php/AIIDE/article/view/12779)） | 不在原子动作上搜，而是在"脚本 + 脚本暴露的选择点"上做前瞻搜索；在 StarCraft 上不输于它用的任何单个脚本 | **最贴合**：我们的"宏动作"（扩经济、造某兵、设防、做任务）就是脚本，选择点是兵种、工厂数、防御规模 |
| 宏观规划：计划模拟 | MCPlan（[Chung, Buro, Schaeffer 2005](https://ualberta.scholaris.ca/items/51aa2466-9520-4cf6-b809-2f6b012e993a/full)）；策略模拟 + 纳什均衡（Sailer, Buro, Lanctot 2007，[pdf](https://skatgame.net/mburo/ps/rtsmc.pdf)） | 生成若干高层计划，与对手的若干计划两两模拟，打分成收益矩阵，按纳什均衡选；计划持续时间长，所以搜索量小 | **对手不确定时的选法**：对手（Brain、原版敌人）可能速攻、发育、龟缩，用小矩阵求稳妥的选择 |
| 滚动时域 | 滚动时域进化 RHEA / 模型预测控制（[RHEA 双人版](https://ar5iv.labs.arxiv.org/html/1607.01730)） | 在前向模型里优化一串动作，只执行第一步，然后重新规划 | 执行方式：每隔几分钟或遇到大事重算 |
| 大分支的采样 | NaïveMCTS（[Ontañón，JAIR 2017](https://arxiv.org/pdf/1710.04805)） | 组合多臂老虎机采样，处理同时、持续的动作 | 候选太多时的备选；目前候选只有几十个，用不上 |
| 策略集扩张 | Double Oracle / PSRO（[综述](https://arxiv.org/html/2403.02227v2)） | 从小策略集开始，每轮加入对当前均衡的最优应对，直到收敛 | 对手模型集合变大时再用 |
| 战斗微操 | Portfolio Greedy Search（[Churchill & Buro 2013](https://www.cs.mun.ca/~dchurchill/publications/pdf/combat13.pdf)）、Stratified Strategy Selection（[Lelis，IJCAI 2017](https://www.ijcai.org/Proceedings/2017/0522.pdf)） | 在单位脚本组合上做爬山/分层搜索，几十到上百单位、毫秒级 | 以后改控兵层用；不是这次的事 |
| 层次化 | Hierarchical Portfolio Search（Prismata，进入人类天梯前 25%）、Adversarial HTN（[Ontañón 2015](https://mlanthology.org/ijcai/2015/ontanon2015ijcai-adversarial)） | 每层一个抽象，从"怎么赢"到"单位命令" | 整体分层的参照 |

结论：RTS 领域里宏观决策成熟、可落地的做法是 **"在宏动作组合上，用抽象前向模型做模拟搜索，滚动重算"**（Puppet Search / MCPlan 一系），配上 **Lanchester 战力模型** 和 **对手模型的小收益矩阵**。我们已经有其中最难的两块：一个很准的经济模型（建造顺序与时间线），和 Lanchester 战力估算。缺的是：对手力量的预测、把经济时间线换算成"我方守家能力曲线"、宏动作集合，以及在上面搜索的指挥器。

## 设计

**1. 抽象前向模型（`expansion.ops.Sim`）。** 以 10 秒为一步推进到一个时域（比如 12 分钟），记录：
- 我方：每个时刻的兵（来自经济模型对该方案的时间线：第几分钟出第几个兵，受单位上限约束）、炮塔（防御规划的炮塔与建成时间）、库存与收入。
- 对方：现有战斗单位，加上已有兵工厂的产出（按工厂的配方时间）；对方是会建造的 AI 时，用我们自己的经济模型做对称估计（同样的起点，最快几分钟出兵、之后的产出速度）；有波次的地图按刷怪表加上走到我方核心的时间。
- 交战：对方兵力到达我方核心时，按 Lanchester 平方律结算我方守家兵力 + 炮塔（炮塔战力用实测容量表）对对方；我方进攻时同理结算对方基地的守备。

**2. 宏动作（脚本 + 选择点）。** 都是已有能力的包装，不新写规则：
- 经济/造兵：`unit:makers`（兵种、工厂数是选择点），由经济规划器出时间线；
- 防御：用防御规划器，规模和"只用库存/建经济来付"是选择点；
- 地图任务：任务要求的建筑、物品、兵，作为必须满足的目标进入打分；
- 进攻：控兵层已有的出击判断（Lanchester）在模拟里一样用来估计何时能推。

**3. 打分（目标函数）。** 时域内：
- 生存：我方核心在任何时刻都没被击破（被击破的方案直接最差）；
- 在此之上比较：时域末的我方战力与经济价值、对方损失（拿下敌方核心的时间越早越好）、地图任务完成得越早越好；
- 参数少而明确（权重），用对战批量结果来调，不按单局打补丁。

**4. 选择。** 候选是"宏动作序列"（第一步 × 第二步，几十个）。对每个对手模型（比如：保持现在的产出、对称速攻、对称发育）各模拟一遍，得到小收益矩阵：
- 一开始用最坏情况（对所有对手模型取最差，再选最好的）；
- 需要时换成矩阵博弈的纳什解（小线性规划，自己写单纯形，不加依赖）。

**5. 执行与重算。** 执行最优序列的第一步（交给经济执行器 `Hand`），每 2–3 分钟或遇到大变化（对方兵力突增、我方建筑大量被毁、任务推进）重算一次。重算只用模型、不做布局，选定后才做布局。

**6. 位置。** 放进模组（`src/expansion/ops/`），不分敌我，同一套代码当玩家打战役、对战 Brain、当敌方 AI。`Match` 只负责开局和记录。

## 先做什么

1. 对方力量预测，和我方"守家能力曲线"（从经济时间线和防御规划换算），先只打印出来，和实际对局对照，校准到大致准确。
2. 宏动作的模型评估（只用模型、不布局），测一次评估要多久；要快的话，在多核上并行评估候选。
3. 指挥器：候选生成、模拟、最坏情况选择、滚动重算，替换 `Match` 里的阶段表。
4. 用线 2 的 20 张图、线 1 的战役关卡批量检验；然后接入地图任务、纳什选择。

今天加的规则（第一阶段 1 座工厂、任务直接变阶段）在指挥器接手后去掉；压力触发和核心挨打触发已经撤掉。
